Why slonbase

A backend in minutes.
Your data where it belongs.

Define collections in a dashboard and get a REST API, auth, realtime and files right away, with every table a real PostgreSQL table you can query, replicate and back up.

Auth and access rules

Password, OAuth2, one-time password and MFA sign-in, email flows, and per-collection API rules in one small filter language, compiled to SQL your indexes can use.

Real PostgreSQL tables

Each collection is a table in the slonbase schema. Query it with SQL, replicate it, pg_dump it, or run it on a managed service.

Realtime for every change

A trigger on each table announces every write, whoever makes it: the API, SQL, auth flows or another program. Subscribers see it, with their rules applied.

Scales out

Run several instances on one database behind any load balancer. Realtime, schema changes, settings and rate limits are shared through LISTEN/NOTIFY. No sticky sessions.

Extend it your way

JavaScript hooks for requests, records, realtime, files and mail, plus routes, cron jobs, migrations and a query builder. Or embed it as a Rust library.

Operations built in

Rate limits, sign-in lockout, request logs, scheduled backups to S3 with a history, Prometheus metrics, projects on one server, roles and API keys, and upgrades tested from the first release.

Many projects, one server

Each project is an isolated installation with its own users, collections, settings and database, on one server or several, run from a command center that shows requests, errors and latency side by side.

An SQL console and designers

Query your data in the dashboard (read-only unless you allow writes), and design your emails and your sign-in page with a live preview, with your name, colours and logo everywhere.

Roles and API keys

Owner, Admin, Developer and Viewer roles for the people who run it, and API keys with a role, an expiry and allowed IPs for scripts and CI.

The dashboard

A dashboard you'll enjoy.

Live grids, a schema editor, API rules, logs, an SQL console and a command center for every project. It follows your light or dark theme, takes your accent colour and your logo, and ⌘K jumps anywhere.

Developer experience

Write less backend.
Ship the app.

A typed client SDK, a filter language your rules and queries share, hooks for the logic that's yours, and SQL whenever you want it. Use the PocketBase SDKs you may already know: they work with slonbase's API.

  • Filters and API rules, relation paths, @request.* and @collection.*
  • Auth with passwords, OAuth2 providers, one-time passwords and MFA
  • Batch requests in one transaction, expand, files and thumbnails
  • Clear, field-level validation errors your forms can show as they are
import PocketBase from "pocketbase";

// the PocketBase JS SDK works with slonbase's API
const pb = new PocketBase("http://localhost:8090");

await pb.collection("users")
  .authWithPassword("ann@example.com", "secret");

const posts = await pb.collection("posts").getList(1, 20, {
  filter: 'published = true && views > 100',
  expand: "author",
});

// realtime
pb.collection("posts").subscribe("*", (e) => {
  console.log(e.action, e.record.title);
});
// hooks: your logic, next to your data
onRecordCreateRequest((e) => {
  if (!e.auth) throw new ForbiddenError("Sign in first.");
  e.record.set("author", e.auth.id);
  e.next();
}, "posts");

routerAdd("GET", "/api/top", (e) => {
  const rows = arrayOf(new DynamicModel({ title: "", views: 0 }));
  $app.db().select("title", "views").from("posts")
    .where($dbx.hashExp({ published: true }))
    .orderBy("views DESC").limit(10).all(rows);
  return e.json(200, rows);
});

cronAdd("cleanup", "0 3 * * *", () => {
  $app.db().delete("posts", $dbx.hashExp({ status: "spam" })).execute();
});
-- every collection is a real table: query it, join it, index it
SELECT a.name, count(*) AS posts, sum(p.views) AS views
FROM slonbase.posts p
JOIN slonbase.users a ON a.id = p.author
WHERE p.published
GROUP BY a.name
ORDER BY views DESC;

-- and changes made here reach realtime subscribers too
UPDATE slonbase.posts SET featured = true WHERE views > 10000;

Resident memory of the server process only. slonbase and PostgREST keep their data in a PostgreSQL server, whose memory is not counted; PocketBase's SQLite runs inside its process. The PostgreSQL server is shared by every instance.

Where each one wins. slonbase is ahead on throughput in every scenario measured here: by 1.2× (sign-in, which bcrypt bounds) up to 68× (filtered lists) against PocketBase, and by 1.2× up to 3.8× against PostgREST. It isn't free: slonbase and PostgREST need a PostgreSQL server (its memory isn't counted in these figures), and PocketBase is one file with nothing else to run. PostgREST is much lighter, with a resident process of 15 MB and a 4.5 MB download, because it does much less: no sign-in, files, realtime or dashboard. Sign-in is bound by bcrypt on all of them. One 4-vCPU VM, loopback, database on the same cores as the server: the numbers show how the three compare here, and they will differ on your hardware.
How it compares

Different tools,
different trade-offs.

slonbase began with an idea from PocketBase and has grown into its own platform, built from scratch in Rust for PostgreSQL. It keeps the PocketBase SDK API, so existing apps, hooks and data carry over. PostgREST is the other thing people reach for on PostgreSQL: a very lean REST layer with nothing else attached. Choose slonbase when

you want PocketBase's way of working on PostgreSQL: SQL access to your data, several instances, managed databases, replicas, and a bigger ceiling for lists and filters.

Choose PocketBase when

you want zero moving parts: one file, SQLite inside, nothing else to run, one small app on one small machine, or you extend it in Go.

Choose PostgREST when

you already manage your PostgreSQL schema and only need a fast REST layer in front of it, with row-level security, and you handle sign-in, files and realtime elsewhere.

Scale out

From one binary
to a fleet.

Start with one instance. When you need more, add instances behind any load balancer, a pooler, or other PostgreSQL servers. Each layout below was run and tested, not just drawn.

Shared through PostgreSQL

Tokens, schema, settings, rate limits, realtime events and cron all coordinate through the database. Any load balancer works with no sticky sessions: a sign-in on one instance is valid on all, and changing a password or "sign out everywhere" ends a token on every instance at once.

Mind the connections

Each instance and each project holds PostgreSQL connections: at most N × (18 + 5 × projects). Lower the pools, raise max_connections, or put PgBouncer in front with a direct connection for LISTEN. Health warns before you run out.

Files need S3 or a shared volume

Local file storage belongs to one instance. Use S3 or one mounted directory, and stop all instances to upgrade: rolling upgrades are not supported yet. The guide says what was tested, and where the limits are.

Questions

Frequently asked.

The short answers. The full ones are in the about page, the feature list and the documentation.

What is slonbase?

slonbase is an open-source backend platform on PostgreSQL. One Rust binary gives you a REST and realtime API, authentication with roles, file storage, JavaScript hooks and an admin dashboard that manages many projects. Every collection is a real PostgreSQL table, and it is self-hosted under the Apache 2.0 license.

Is slonbase a PocketBase clone or fork?

No. slonbase is a separate codebase written from scratch in Rust for PostgreSQL, with its own dashboard and features such as many projects in one installation, roles and API keys, an SQL console and scale-out across instances. PocketBase inspired the idea, and slonbase keeps its API shape on purpose, so the PocketBase SDKs, hooks and data carry over.

Do I need to install PostgreSQL myself?

slonbase needs PostgreSQL 14 or newer, which it does not bundle. On Debian, Ubuntu, Fedora and RHEL the one-command installer installs PostgreSQL if the machine has none, creates the database and role, and sets slonbase up. You can also point it at an existing or managed PostgreSQL.

How does slonbase compare with PocketBase and PostgREST?

PocketBase is one Go binary with SQLite inside, and PostgREST is a lean REST layer over a PostgreSQL schema. slonbase is a whole backend platform on PostgreSQL. In the public benchmark on one 4-vCPU machine it served 4.9 times as many list requests per second as PocketBase and 2.1 times as many as PostgREST. Each comparison page lists what differs and when to choose which.

Is slonbase ready for production?

slonbase follows Semantic Versioning with a written stability promise, is tested against the PocketBase SDKs, is upgraded in place from every release in continuous integration, and publishes its security reviews. As with any software that holds your data, back up before upgrading and test your own workload.

How do I move from PocketBase?

Run slonbase import-pocketbase on your pb_data folder or a backup zip. It brings over collections, records with their password hashes, files and settings, and the PocketBase SDKs work against slonbase's API. The migration guide lists the few differences.

Can one slonbase host several apps?

Yes. Projects are isolated installations inside one slonbase process, each with its own users, collections, settings and database, managed from a command center in the dashboard.

Can I run several slonbase instances behind a load balancer?

Yes, with no sticky sessions: tokens, schema, settings, rate limits and realtime are shared through PostgreSQL, and a sign-in on one instance is valid on all. Plan the PostgreSQL connections (each instance and project holds some; PgBouncer in transaction mode works with a direct connection for LISTEN), keep files on S3 or a shared volume, and stop all instances to upgrade. The scaling guide lists the tested layouts and the limits.

What does it cost, and under which license?

slonbase is free and open source under the Apache 2.0 license, with no limits on users, projects or instances. You host it yourself, so your costs are your own server and PostgreSQL.

Get started

Install it your way.

One command on Linux, or Docker. slonbase connects to any PostgreSQL 14+ server, and the installation guide starts from a bare server.

# Debian, Ubuntu, Fedora, RHEL: installs PostgreSQL if needed, creates its role and database,
# installs slonbase and creates your first superuser
curl -fsSL https://slonbase.com/install.sh | sudo sh
mkdir slonbase && cd slonbase
curl -fsSLO https://raw.githubusercontent.com/ayeshrodz/slonbase/main/compose.yaml
echo "POSTGRES_PASSWORD=$(openssl rand -hex 24)" > .env
docker compose up -d
docker compose logs slonbase | grep "setup?token"
curl -fsSL https://slonbase.com/slonbase.gpg | sudo tee /usr/share/keyrings/slonbase.gpg > /dev/null
curl -fsSL https://slonbase.com/slonbase.list | sudo tee /etc/apt/sources.list.d/slonbase.list
sudo apt update && sudo apt install slonbase
sudo journalctl -u slonbase | grep "setup?token"
sudo curl -fsSL -o /etc/yum.repos.d/slonbase.repo https://slonbase.com/slonbase.repo
sudo dnf install slonbase
sudo journalctl -u slonbase | grep "setup?token"
curl -fsSLO https://github.com/ayeshrodz/slonbase/releases/download/v2.2.0/slonbase-2.2.0-linux-amd64.tar.gz
tar xzf slonbase-2.2.0-linux-amd64.tar.gz
./slonbase serve    # prints the setup link
# collections, records, password hashes, files and settings, from pb_data or a backup zip
slonbase setup --database-url "postgres://..." --email you@example.com --password '...'
slonbase import-pocketbase ./pb_data
cp pb_hooks/*.pb.js slonbase_hooks/   # your hooks keep working
slonbase serve

Or deploy with one click on Render, or with the setups for Fly.io and others. Packages update with apt upgrade and dnf upgrade (repository details).
